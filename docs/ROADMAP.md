# Roadmap стабилизации и модернизации проекта Formatter

> Статус документа: рабочая версия от 2026-05-29.
> Назначение: зафиксировать безопасный порядок развития проекта, чтобы рефакторинг шёл фазами, а не хаотично.
> Этот файл — справочник для будущих итераций. При изменении кода обновляйте соответствующие разделы.
> **Текущий прогресс и «что дальше» — в [PROGRESS.md](./PROGRESS.md).** Маркеры статуса у фаз ниже: ✅ сделано · 🔄 в работе · ⬜ не начато.

## 1. Executive Summary

Formatter — компактное приложение на Spring Boot 3.3.3 / Java 21 (~1700 строк Java) со статическим фронтендом на ванильном JS (~2900 строк HTML/CSS/JS). Назначение: форматирование/валидация JSON и XML, нормализация и дедупликация логов.

Приложение **функционально и работает**. Архитектура (controller → service → util → model) для текущего масштаба адекватна и **переусложнять её не нужно**. Главные проблемы — не «неправильная архитектура», а накопленный технический долг 2-го порядка:

- нет ни одного теста при том, что вся ценность приложения — в чувствительной к крайним случаям парсинг-логике;
- дублирование ключевой логики (балансировка скобок JSON реализована трижды, SHA-256 — трижды);
- мёртвый код (`LogExtractor`, `BracketExtractor`, `HashUtil`, `XmlUtils.minify`);
- XSS на фронтенде через `innerHTML` + неэкранированный контент логов;
- отсутствие логирования и глобальной обработки ошибок;
- `CORS *`;
- монолитный `app.js` на 1262 строки с глобальным состоянием.

**Стратегия roadmap'а:** сначала зафиксировать поведение тестами и убрать мёртвый код (нулевой риск), затем устранить дубли и закрыть безопасность, и только потом — структурные улучшения и подготовка фронтенда. Никаких переписываний, миграций на фреймворки или декомпозиции «на вырост». Каждый шаг обратим и не ломает текущую функциональность.

## 3. Main Technical Risks

| ID | Риск | Где | Последствие |
|----|------|-----|-------------|
| R1 | **Нет тестов** | `src/test/` пуст | Любой рефакторинг парсинга — вслепую; регрессии незаметны |
| R2 | **XSS** | `app.js:108` (`highlightText` возвращает сырой текст), `app.js:254–352` (`innerHTML`) | Исполнение `<script>` из вставленного лога; `escapeHtml` в коде отсутствует |

## 4. Safe Short-Term Improvements (нулевой / низкий риск)

Можно делать сразу, до тестов, потому что поведение не меняется:

1. **Удалить мёртвый код** (после `grep`-проверки, что вызовов нет): `LogExtractor.java`, `BracketExtractor.java`, `HashUtil.java`, метод `XmlUtils.minify`. Снижает шум, убирает ложные «источники правды».
2. **Закрыть CORS**: заменить `allowedOrigins("*")` на `allowedOriginPatterns(...)` или чтение origin из конфигурации/переменной окружения. Для однопортового деплоя (фронт+бэк на одном origin) — почти нулевой риск.
3. **Эскейп на фронте**: ввести `escapeHtml(str)` и применить к `item.pretty`, `item.description`, `item.key`, `item.hash` перед вставкой в `innerHTML`. Закрывает R2 минимальными правками (до полного перехода на DOM-узлы).
4. **Убрать `console.log` с эмодзи** из продакшн-путей `app.js`.
5. **Унифицировать `Boolean`-флаги** через `FormatOptions.defaults()`, чтобы убрать разбросанные `Boolean.TRUE.equals(...)`.

**Польза:** меньше кода, закрыты две дешёвые дыры (XSS, CORS), чище чтение.
**Риск:** низкий. **Предусловие:** сборка проходит после удаления (проверить компиляцией).

## 5. Medium-Term Refactoring Plan

Выполнять **только после появления тестового фундамента** (раздел 8):

1. **Свести три копии `extractCompleteJson` в один класс** (`JsonBalancer` / `JsonBoundaryFinder`). Все вызовы — на него. Предварительно зафиксировать текущее поведение «золотыми» тестами, т.к. реализации расходятся в обработке `\`.
2. **Свести SHA-256 к одному методу** — `HashUtil.sha256` (он уже существует, но не используется). `LogService.sha256` и цикл в `JsonUtils.canonicalHash`/`XmlUtils` перевести на него.
3. **Разбить `LogService.normalize`** (LogService.java:47–177) на приватные шаги внутри того же класса: `parse → filter → extractPatterns → dedup → buildExport`. Без выноса в новые классы на этом этапе.
4. **Вынести regex-`Pattern` из цикла**: в `extractMessageDescription` (LogService.java:235) компиляция паттерна происходит на каждой записи — поднять в статические константы.
5. **Стабилизировать wrap/unwrap**: уйти от regex-постобработки pretty-вывода (`formatWithCompactValues`) в пользу управляемой сериализации. Высокий риск (видимое UX-обещание «`{"value": ...}` в одну строку») — делать со снимком вывода до/после побайтно.
6. **Консолидировать «магический ключ `value`»**: сейчас о нём знают и `JsonUtils.formatTabbed` (строки 99–133), и `JsonService.formatWithCompactValues`. Свести к одному месту.

## 6. Frontend Modernization Strategy

Фронтенд — главная долгосрочная забота, но **немедленная миграция на React/Vue не оправдана** при текущем размере. Порядок действий — от дешёвого и безопасного к дорогому:

### Этап A — гигиена (без смены технологий)
- Ввести `escapeHtml` и заменить сборку карточек через `innerHTML` (app.js:254–352) на построение DOM-узлов. Закрывает XSS и убирает зависимость от `onclick`-строк в шаблонах.
- Единый HTTP-слой: всё через существующий `postJson`. Сейчас wrap/unwrap бьют `fetch` напрямую (app.js:859, 921) и дублируют ~60 строк — свести к `jsonAction("wrap"|"unwrap")`.
- Заменить `alert()` (4 вхождения) и `prompt()` (app.js:1103) на единый `showNotification` / неблокирующие диалоги.

### Этап B — модульность (всё ещё ванильный JS)
- Разнести `app.js` на ESM-модули по разделам: `logs.js`, `json.js`, `xml.js`, плюс общие `api.js`, `ui.js`, `state.js`. Подключение через `<script type="module">`.
- Свести 6 глобальных переменных к одному простому модулю состояния (`state.js`) — без внешних библиотек.

### Этап C — консистентность
- Вынести все русские строки UI в один словарь (заготовка под i18n), убрать смесь русского и английского в подписях.
- Убрать hardcoded inline-стили из `app.js`, опираться только на CSS-переменные.

### Этап D — визуальный редизайн (явное пожелание владельца)

> **Важно (со слов владельца, 2026-05-29):** текущий фронт визуально не нравится — выглядит «скупо» и дёшево. Нужен **по-настоящему современный дизайн**: красивое, аккуратное отображение, **неброская, но интересная палитра** (приглушённые, но небанальные цвета — не «кричащие»). Это не косметика поверх текущего, а серьёзная переработка интерфейса.

Конкретные требования к UX/UI (фиксируем как цель, реализуем после Этапов A–C):
- **Удобный ввод и вывод.** И поле ввода, и область результата должны быть просторными, читаемыми, с понятной визуальной иерархией; явное разделение «вход → действие → выход».
- **Ключевые кнопки — функциональные и заметные.** Главные действия (Pretty / Minify / Validate / Wrap / Unwrap / нормализация логов) должны явно выделяться; второстепенные — спокойнее. Понятные состояния (hover/active/disabled).
- **Включение/выключение функций — наглядно.** Переключатели опций и режимов (например, выбор паттернов логов, флаги XML) должны читаться сразу, с явным активным/неактивным состоянием.
- **Современная подача:** аккуратная типографика, продуманные отступы, сетка, мягкие тени/радиусы, тёмная/светлая темы на CSS-переменных, плавные ненавязчивые переходы.

Подход к реализации редизайна — выбрать ближе к делу (обсудить с владельцем):
- **Вариант 1 (ниже риск):** глубокая переработка стилей/разметки на текущем ванильном стеке (после модульной подготовки A–C). Дёшево, без новых зависимостей.
- **Вариант 2 (выше потолок качества):** перейти на компонентный фреймворк (например, Vue/Svelte/lit) + готовую дизайн-систему/набор компонентов. Оправдано именно из-за запроса на серьёзный редизайн.

### Когда миграция на фреймворк станет оправданной
С учётом явного запроса на редизайн миграция из «гипотетической» становится **реальным кандидатом**. Триггеры, при которых она однозначно оправдана:
- решено делать полноценный визуальный редизайн с компонентной дизайн-системой (Этап D, вариант 2);
- интерактивных экранов становится существенно больше (формы, состояние, маршрутизация);
- ручное управление DOM начинает давать баги синхронизации состояния.

Порядок остаётся прежним: **сначала** структурная подготовка (Этапы A–C на ванильном JS), **потом** решение по фреймворку и редизайн. Это снижает риск и не блокирует текущую работу.

## 7. Backend Stabilization Strategy

1. **Логирование**: подключить `slf4j` (уже транзитивно есть в Spring Boot). Заменить `catch (Exception ignore) {}` и `System.out` на осмысленные `log.warn/error`. Не глотать исключения молча.
2. **Глобальная обработка ошибок**: `@RestControllerAdvice` с единым форматом ответа (на базе существующего `FormatResponse` с полем `errors`). Сейчас часть ошибок уходит в `errors: []`, часть — в дефолтный Spring 500.
3. **Границы util/service**: `UniversalJsonExtractor` содержит бизнес-правила («починка» невалидного JSON) — концептуально это `service`, а не `util`. Перенос — на этапе структурных улучшений, не срочно.
4. **Диспетчеризация форматов**: рукописный `switch` в `FormatController.dispatch` пока терпим. Переход на `Map<String, FormatStrategy>` оправдан только при добавлении 3-го+ формата (YAML/CSV).
5. **Производительность парсинга логов**: пересмотреть O(n²)-участки в `UniversalJsonExtractor` (`findAllJsonInText:62`, `fixInvalidJson` с `matches(".*...$")`) — после тестов, при подтверждённой проблеме на больших логах. Не оптимизировать преждевременно.

## 8. Testing Strategy

Тесты — **предусловие** для всего среднесрочного рефакторинга. Цель не 100% покрытие, а защита ключевых инвариантов.

### Приоритет 1 — «золотые» тесты на текущее поведение (характеризационные)
Зафиксировать вход → выход на реальных данных **до** любых правок дублей:
- `JsonService`: pretty / minify / validate / wrap / unwrap — по 1–2 эталона, включая wrap с пустыми и текстовыми значениями.
- `XmlService`: pretty / minify (python-style) / validate; кейс с `keepXmlDeclaration` и с комментариями.
- `LogService.normalize`: реальный многострочный лог с `internalRequest`/`response`/`args=[{...}]`; проверить дедупликацию (одинаковый JSON → один блок) и спец-фильтр `{"timestamp"...}`.
- `JsonUtils.canonicalize` / хеши: стабильность хеша при перестановке ключей.

### Приоритет 2 — крайние случаи парсинга
- `extractCompleteJson`: вложенные `{}`/`[]`, экранированные кавычки `\"`, скобки внутри строк, обрыв на середине.
- `UniversalJsonExtractor.fixInvalidJson`: лишние `}` и `]` в хвосте.

### Приоритет 3 — безопасность/контракты
- XXE: убедиться, что внешняя сущность в XML не резолвится.
- (Фронт, опционально) проверка `escapeHtml` на `<script>`.

**Инструменты:** JUnit 5 + `spring-boot-starter-test` (уже в `pom.xml`). Для контроллеров — `@WebMvcTest`. Фиктивные данные хранить в `src/test/resources`.

## 10. Future Scalability Considerations

- **Новые форматы** (YAML, CSV): добавляются как новый `*Service` + ветка в `dispatch`. При 3-м формате — перейти на реестр стратегий. Декомпозиция в отдельные модули не нужна.
- **Новые типы логов**: сейчас семантика (`request`/`response`/`service fields`) вшита в `LogService` через `Set` и `List<KeyPattern>`. При росте числа правил вынести их в каталог `LogPatterns` (enum/record) — это снимет дублирование при добавлении парсеров.
- **Объёмы данных**: лимиты уже есть в `application.yml`. При работе с очень большими логами — пересмотреть O(n²)-участки (раздел 7).
- **Принцип**: расширяемся в пределах текущего монолита, пока он читается. Монолит здесь — преимущество, а не долг.

## 12. Recommended Development Principles

- **Сначала тест, потом рефакторинг.** Любая правка дублирующейся или парсинг-логики — после характеризационного теста.
- **Инкрементальность.** Маленькие обратимые шаги, каждый компилируется и проходит тесты.
- **Один источник правды.** Дублирующуюся логику (скобки, хеш, формат экспорта, ключ `value`) сводить в одно место.
- **Пропорциональность масштабу.** Не вводить абстракции «на вырост»; стратегии/модули — только когда появляется третий случай.
- **Не глотать ошибки.** Никаких пустых `catch`; логировать.
- **Безопасность по умолчанию.** Любой пользовательский контент в DOM — только через эскейп; никаких `*` в CORS на проде.
- **Объяснять перед крупной правкой.** Для шагов среднего/высокого риска — фиксировать причину, риск и ожидаемый эффект.

## 15. Backlog расширения функционала (на будущее, в самом конце)

> Зафиксировано по просьбе владельца (2026-05-29). Это **не текущая работа**, а копилка идей для этапа, когда стабилизация завершена и пора растить функционал. Конкретику и приоритеты обсудим отдельно; здесь — направления и кандидаты для предложений.

**Текущее ядро (что есть):** форматирование/валидация JSON, форматирование/минификация/валидация XML, нормализация больших логов (извлечение JSON-сообщений с отсевом лишнего).

**Направления роста (кандидаты — обсудить и приоритизировать):**
- **GraphQL** (владелец работает с ним): форматирование/«pretty» запросов и схем (SDL), валидация синтаксиса, возможно — извлечение/просмотр операций. Вероятно, самый востребованный следующий формат.
- **Новые форматы данных:** YAML, CSV/TSV (в т.ч. конвертация JSON↔YAML, CSV↔JSON), возможно TOML/`.properties`.
- **Утилиты-инструменты:** декодирование JWT, Base64 encode/decode, URL-encode, разворачивание/просмотр escape-строк, генерация/проверка хешей.
- **Сравнение и diff:** структурный diff двух JSON/XML (уже есть каноникализация и хеши — хорошая база).
- **Валидация по схемам:** JSON Schema, XSD для XML.
- **Работа с логами (развитие):** настраиваемые правила извлечения/паттернов через UI, фильтры, экспорт в разных форматах.
- **Анализ сообщений по уровню/типу (запрос владельца 2026-05-30).** Сейчас логи только извлекают JSON из строки; семантического анализа нет. Идея, выросшая из фильтра «request/response/internal…»: на уровне отдельного сообщения распознавать и анализировать не только payload, но и **уровень (INFO/DEBUG/ERROR)**, ошибки, internal/external контекст. Это превращает «извлекатель JSON» в «анализатор логов». Реализовывать в рамках работы с сообщением: бэкенд должен возвращать `level`/`traceId`/тип в модели item (сейчас в item нет `raw`, `level` всегда INFO, поэтому фильтры INFO/DEBUG/ERROR неактивны; работают только request/response/internal/external по `key`). Фильтр в UI оставлен как задел под эту функцию.

**Архитектурное замечание.** Каждый новый формат добавляется как отдельный `*Service` + ветка в диспетчере; при 3-м+ формате — перейти на реестр стратегий `Map<String, FormatStrategy>` (см. §5/§7). Это, а не микросервисы/декомпозиция, — правильный способ расти в текущем масштабе. Декомпозиция (Phase 6) рассматривается только при кратном росте.

**Что от меня (ассистента) ожидается на этом этапе:** предлагать конкретные варианты расширения, оценивать их сложность/риск и вписывать в общую архитектуру так же осторожно и инкрементально, как стабилизацию.
